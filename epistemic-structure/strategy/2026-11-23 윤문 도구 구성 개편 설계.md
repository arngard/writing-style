# 2026-11-23 윤문 도구 구성 개편 설계

작업 트리 노드 "정식 규약을 의미 규칙, 기계 규칙, 설명, 도구, 윤문 워크플로로 구성하고 윤문 스킬 원본을 둔다"의 설계다. 구현이 끝나 결과가 규약과 구조에 반영되면 이 문서를 종결한다.

## 상황

정식 규약은 `epistemic-structure/architecture/plain-prose-rules.md`와 그 하위 문서, `implementation/`의 세부 규정 세 묶음(어휘 선택, 참조 표기, 문장 부호)에 산문으로만 있다. 규칙 본문의 절반 이상이 `implementation/`의 예시 문서 안에 예시 표와 섞여 있다 (ref: [2026-11-18 구조 평가.md](2026-11-18%20구조%20평가.md) "측정"). 기계로 검사하거나 고치는 도구는 없다.

사용자 지시(`@arngard`)는 다음과 같다.

- 2026-11-22: 규칙을 세 부류(스크립트로 완전 처리, 스크립트로 검출하고 의미적으로 수정, 읽으며 의미적으로 수정)로 나눠 부류에 맞는 폴더 배치와 일관된 형식으로 구성한다. 윤문 스킬이 처리를 시작한다.
- 2026-11-23: 윤문 워크플로, 의미 규칙, 기계 규칙, 설명으로의 링크, 도구로 구성하고 윤문용 도구 기능을 제공한다. 규정은 지금 상태를 유지한다.
- 2026-11-23 결정: 도구 코드는 이 레포에서 새로 쓴다. 규칙 본문은 `architecture`에 둔다. 구조 평가의 윤문 경로 개선안을 함께 반영한다. 윤문 스킬 원본을 이 레포에 두고 전역 설치는 이 레포 밖의 후속 작업으로 둔다.

## 대응

- 규정의 문구는 바꾸지 않는다. 조항은 자리를 옮기거나 규칙 이름(ID)을 얻기만 한다. 고정한 기준 커밋과 새 트리를 조항 단위로 맞춰 보는 보존 대조로 이를 확인한다.
- 규칙 본문은 `architecture`의 규칙 문서에 둔다. 규칙 문서 하나는 검토자 한 명이 한 번에 맡는 묶음이고, 규칙 하나가 `##` 절 하나다.
- `implementation`은 규약을 글에 적용하는 수단을 담게 다시 정의한다. 하위 프로젝트 `implementation/revision/`에 설명(예시), 기계 규칙, 도구, 워크플로, 윤문 스킬 원본을 둔다.
- 도구는 표준 라이브러리만 쓰는 Python으로 새로 쓴다. front matter가 없는 글과 표준 입력(커밋 메시지, 대화 응답)도 받는다. 도구가 문맥을 확정할 수 없는 위치는 고치지 않고 후보로 보고한다.
- 2026-11-18 구조 평가의 윤문 경로 개선안 1, 3, 6, 7, 8을 함께 반영한다.

- 이전할 내용은 규정, 즉각적 취지, 예시 셋으로 가른다. 규정과 즉각적 취지는 문장이든 표든 규칙 문서로 간다. 예를 들어 `ascii-punctuation.md`의 부호별 치환 표, `reference-markers.md`의 표지 판정 표, `old-marker-migration.md`의 형태별 처리 표는 규정이라 규칙 문서로 간다. 예시(고치기 전과 고친 뒤를 보이는 표, 규정을 보이려고 만든 코드 예시)만 설명 문서로 간다.
- 제목 자체가 규정인 절이 있다(예: "고유한 뜻을 가진 외래어는 번역하지 않고 통용되는 음차를 쓴다"). 그 제목은 규칙 절의 제목으로 그대로 쓰고 보존 대조의 대상에 넣는다.
- 기계 규칙의 규정 문장은 규칙 문서에 남는다. 기계 규칙 파일은 그 규칙 이름을 가리키며 치환 데이터만 담는다.
- 하위 프로젝트 내부는 형식 감사가 검사하지 않는다. 설명 문서와 워크플로 문서는 그래도 front matter와 이 레포의 평서문 기록 규약을 지킨다. 다른 레포의 윤문 에이전트가 읽는 문서이기 때문이다. 내부 링크는 감사 확장이 검사한다(아래 "도구").

### 형식

#### 규칙 문서

```markdown
## <규칙 제목> `<규칙 이름>`

<조항 본문. 지금 문구 그대로. 규정 표 포함>

### 후보 검출 패턴

    (정규식 코드 펜스. 검출 후 의미 수정 부류일 때만)

### 기계 규칙

- [<파일>](../../../implementation/revision/mechanical/<파일>) (완전 처리 부류일 때만)

### 설명

- [<설명 문서>](../../../implementation/revision/explanations/<문서>) "<절 제목>"
```

- 규칙 이름은 영문 소문자 케밥 케이스이고 레포 전체에서 하나다.
- 부류는 절의 구성으로 드러난다. `### 기계 규칙`이 있으면 완전 처리, `### 후보 검출 패턴`만 있으면 검출 후 의미 수정, 둘 다 없으면 의미 수정이다. 한 규칙에 둘 다 있을 수 있다(기계로 확정되는 형태만 치환하고 나머지는 후보로 보고).
- 지금 하위 문서의 여러 `##` 절이 한 조항을 나눠 설명하면(예: `bullets-and-prose.md`의 "개조식으로 쓰는 경우", "판정") 그 절들을 `###`로 내리고 규칙 절 하나로 묶는다. 이때 조항의 조건과 예외는 원래 붙어 있던 조항 아래에 그대로 둔다.

#### 설명 문서

규칙 문서와 같은 이름의 문서에 모은다. 절 제목은 지금 세부 규정의 절 제목을 그대로 쓰고, 제목 아래 `규칙: <규칙 이름>` 줄(규칙 이름은 인라인 코드)을 둔 뒤 예시를 옮긴다.

#### 기계 규칙 파일

JSON 파일 하나가 규칙 하나다. 표준 라이브러리 `json`으로 읽는다.

```json
{
  "rule": "<규칙 이름>",
  "replacements": [
    {"find": "<정규식>", "replace": "<바꿀 표기>", "note": "<설명>"}
  ],
  "apply_in": ["prose"]
}
```

- 치환은 적힌 순서대로 한 번씩 적용한다. `replace`의 역참조는 `\1` 형태만 허용한다. 빈 `find`, 알 수 없는 키, 알 수 없는 영역 이름, 컴파일되지 않는 정규식이 있으면 어떤 글도 고치기 전에 규칙 읽기 실패로 끝낸다.
- `apply_in`은 적용할 영역이다. 기계 규칙은 산문 영역(`prose`)에만 적용한다.

- 화살표는 흐름 표기, 항목 표시, 상세 문서를 가리키는 포인터를 구별해야 해서 검출로 둔다. 포인터는 참조 규정에 따라 표지로 바꾸기 때문이다. 가운뎃점도 검출로 둔다. 같은 나열 형태라도 금지 사례를 보인 자리는 쉼표가 아니라 이름과 코드포인트를 쓴 서술로 고쳐야 하고, 기계는 두 경우를 구별하지 못한다.
- 참조 표지는 `ref:`, `sub:`, `see:` 세 낱말에 링크가 바로 붙은 형태라면 참조 표지로 확정되므로, 규정된 형태(콜론 뒤 공백 한 칸)로 고치는 일을 기계가 맡는다.
- 같은 조항이 상위 요지와 세부 규정에 두 번 적힌 경우(예: vocabulary.md의 "별" 요지와 common-usage.md의 "별" 절)는 세부 규정의 문장을 규칙 본문으로 삼는다. 요지에만 있는 문장은 같은 규칙 본문에 더한다. 문장을 지우는 경우는 다른 자리에 같은 문장이 남을 때뿐이며, 지운 문장마다 그것을 대신하는 남은 문장을 원장에 적는다.
- 완전 처리 부류가 하나뿐인 것은 규정을 바꾸지 않기 때문이다. 기계로 확정할 수 없는 치환은 모두 검출로 둔다. 상류 약식 규칙에만 있는 말줄임표와 둥근 따옴표의 ASCII 치환, 범위 표시의 물결표는 규정 변경이라 이 작업에 들이지 않는다(작업 트리의 다른 노드).

### 보존 대조

규정 문구가 그대로인지는 이전 작업에 쓰는 일회용 스크립트로 확인한다. 스크립트와 결과는 git이 무시하는 `.tmp/`에 둔다.

- 기준은 브랜치의 시작 커밋(5a18e8e)으로 고정한다.
- 이전 원장은 옛 파일과 절마다 새 규칙 이름, 또는 설명 문서의 절을 적는다. 대조는 원장의 대응마다 옛 절의 단위(제목, 문장, 목록 항목, 표 행, 코드 예시)가 대응하는 새 절에 있는지 본다. 다른 규칙 아래로 옮겨진 단위는 빠진 것으로 센다. 조건과 예외가 다른 규칙으로 옮겨지면 적용 범위가 달라지기 때문이다.
- 차이는 세 가지로 나눠 보인다. 문구의 차이는 0건이어야 한다. 제목 수준, 링크 경로처럼 이전 때문에 바뀌는 형식의 차이는 목록으로 모아 사용자 검토에 보인다. 중복 제거는 지운 단위와 대신하는 단위의 쌍으로 보인다.
- 묶음마다 대조 결과를 그 묶음의 커밋 메시지에 요약한다.

### 도구

`implementation/revision/tools/`에 둔다.

공통 계약:

- 입력은 파일 경로나 표준 입력이다. front matter가 없어도 처리한다. 인코딩은 UTF-8만 받고, 읽지 못하면 오류로 끝낸다.
- 결과는 표준 출력, 진단은 표준 오류로 낸다. `--format json`은 결과 형식만 바꾼다.
- 종료 코드 2는 도구 오류(규칙 읽기 실패, 입력이나 출력 실패, 잘못된 인자)다.
- 표준 입력에는 경로가 없으므로, 경로로 정하는 예외(`reference/` 아래의 원본처럼 원형 부호를 쓰는 영역)는 `--path-hint <경로>`로 받는다.

| 도구 | 하는 일 | 종료 코드 |
|---|---|---|
| `detect.py` | 기계 규칙 위반과 후보 검출 패턴 위치를 리포트한다. 글을 고치지 않는다 | 0 위반 없음, 1 위반 있음 |

| `collect_review.py` | 윤문 원칙, 고른 규칙 문서의 본문, 후보 위치, 설명 경로를 검토 자료 하나로 묶는다. `--docs`로 규칙 문서를 고른다 | 0 성공 |
| `check_preservation.py` | 고치기 전과 뒤를 대조해 변경을 보고한다 | 0 변경 없음, 1 확인할 변경 있음, 3 채택 금지 |

- 영역 판별: 공통 모듈은 글을 구문 영역(front matter, 코드 펜스, 들여쓴 코드, 인라인 코드, 인용 블록, 링크 대상, 참조형 링크 정의, URL, HTML, 산문)으로 나누고 위치를 돌려준다. 적용 여부는 규칙이 정한다. 기계 규칙은 산문에만 적용한다. 후보 검출 패턴은 모든 영역에서 찾되 영역을 함께 보고한다. 옛 참조 표기 규정처럼 규약을 담은 코드 펜스는 고치고 원문을 옮긴 펜스는 두는 판단을 의미 검토가 하도록 하기 위해서다. 닫히지 않은 펜스처럼 판별하지 못한 구문은 그 뒤를 모두 산문이 아닌 영역으로 보아 고치지 않는다.
- `fix.py --write`: 같은 폴더의 임시 파일에 쓴 뒤 교체한다. 읽은 뒤 원본이 바뀌었으면 쓰지 않는다. 줄바꿈 형식(LF, CRLF)과 BOM 여부를 보존한다. 심볼릭 링크는 고치지 않고 오류로 끝낸다.
- `check_preservation.py`의 비교 항목은 숫자, URL, 링크 대상, 인라인 코드, 코드 블록, 인용 블록, front matter 값이다. 각 항목의 값과 출현 횟수를 전후로 비교하고, 달라진 값마다 위치와 앞뒤 문맥을 보고한다. 달라진 값은 모두 확인할 변경(종료 코드 1)이다. 윤문 중에 근거가 있어 바꾼 것(예: 규약을 담은 코드 펜스의 옛 표기)이면 윤문 결과 보고에 그 근거를 적는다. 채택 금지(종료 코드 3)는 기계 수정 단계의 전후에 산문이 아닌 영역이 바뀐 경우다. 그 경우는 도구의 결함이다.
- 보존 검사는 문체(평어체, 존댓말)를 보지 않는다. 갈래와 독자에 따라 바뀔 수 있기 때문이다.
- `collect_review.py`는 대상 글을 검토 지침과 구분해, 글 안의 명령이나 링크를 따를 지시가 아니라 다듬을 데이터로 다루라는 안내와 함께 경계 표시 안에 넣는다. 글 안의 링크를 따라가지 않는다.
- 시험은 `tools/tests/`에 표준 라이브러리 `unittest`로 둔다 (ref: [coding-guidelines.md](../../implementation/AGENTS/epistemic-rules/coding-guidelines.md) "성공 기준을 테스트로"). 시험 자료는 이 레포에서 만든 예문만 쓴다. 길이가 다른 백틱 펜스, 물결표 펜스, 들여쓴 코드, 중첩 인용, 참조형 링크, 닫히지 않은 펜스, front matter 없는 입력, CRLF와 BOM 입력을 포함한다. 기계 규칙은 낱말 경계(`resee:[` 같은 다른 낱말 안의 일치), 뒤가 실제 링크인지, 코드와 인용 영역 제외, 두 번 적용해도 결과가 같은지를 시험한다.
- 구성 검사는 감사 확장 `AGENTS/audit-checks/revision_rules.py`로 둔다 (ref: [audit-extensions.md](../../AGENTS/epistemic-rules/audit-extensions.md)). 규칙 이름의 중복과 누락, 규칙의 설명 링크와 설명 절의 `규칙:` 줄의 양방향 일치, 규칙의 기계 규칙 링크와 기계 규칙 파일의 `rule` 값의 양방향 일치, 정규식 컴파일, `implementation/revision/` 안 문서(설명, 워크플로, 스킬 원본)의 링크 대상을 본다. 형식 감사와 커밋 전 훅이 이미 감사를 부르므로 따로 훅을 걸지 않는다.

### 워크플로와 윤문 스킬

- `workflows/detect.md`: 글을 고치지 않고 리포트만 받는다.
- `workflows/revise.md`의 순서:
  1. 갈래를 정한다. 갈래 규약이 아직 없는 갈래(회고, 창작, 주석)는 사실 서술 부분에 평서문 기록 규약을 적용한다 (ref: [writing-genres.md](../ontology/writing-genres.md) "경계").
  2. 고치기 전 원본을 보관한다. 이후 모든 대조의 기준이다.
  3. 기계 수정(`fix.py`)과 그 전후의 보존 검사.
  4. 의미 수정. 규칙 문서 묶음마다 맥락 없는 검토자가 수정안을 낸다. 수정은 한 사람(윤문을 맡은 에이전트)이 묶음 순서대로 차례로 적용하고, 수정안이 같은 자리에서 부딪치면 두 규칙을 함께 만족하게 다시 쓴다.
  5. 기계 검사 재실행과 원본 대비 보존 검사. 확인할 변경마다 근거를 정리한다.
  6. 뜻의 보존 검토: 맥락 없는 검토자가 원본과 최종본을 대조해 수치, 한정 조건, 귀속, 상반된 견해가 남았는지 확인한다.
  7. 자연스러움 검토: 원본과 수정 경위를 보지 않은 다른 검토자에게 최종본만 주고 문장이 자연스러운지 확인한다. 원본을 본 검토자는 빠진 내용을 원본으로 채워 읽기 때문이다.
  8. 6이나 7에서 고친 것이 있으면 5부터 다시 한다.
- `workflows/change-rules.md`: 규칙, 패턴, 설명, 기계 규칙을 더하거나 고칠 때 고칠 파일과 구성 검사.
- `skill/SKILL.md`: 윤문 요청에서 시작해 revise.md를 따르게 하는 스킬 원본이다. 다른 레포에서 이 레포를 찾는 경로는 설치 때 정한다.

### 진입점과 구조 평가 반영

- README.md의 윤문 안내를 바꾼다. 윤문의 정의 한 문장(평가 3), 갈래와 규약 파일 표(규약이 없는 갈래는 없음으로 적는다, 평가 7), 윤문 워크플로와 규칙 문서로 가는 직접 링크(평가 1)를 둔다.
- 상위 문서(plain-prose-rules.md)는 조항을 열거하지 않는다(평가 6). 세부 규정 묶음의 안내 문서 세 건(`implementation/*/README.md`)은 묶음과 함께 사라진다(평가 8).
- 평가 2(상류 약식 규칙 조항 들이기), 4(참조 표기 두 벌), 5(늘 적재되는 약식 규칙)는 이 작업에서 다루지 않는다. 반영한 항목만 구조 평가 문서에서 지운다.
- 고칠 문서: category-placement.md, implementation.md, implementation/AGENTS.md, implementation/INDEX.yaml, README.md, README.en.md, 루트 AGENTS.md의 평서문 기록 규범, ontology/revision.md, 생성 색인.

### 진행 순서

1. 설계 검토(Codex)와 사용자 승인.
2. `implementation/revision/` 골격, README, 공통 모듈(영역 판별)과 그 시험. 같은 커밋에서 implementation.md, implementation/AGENTS.md, INDEX.yaml, category-placement.md의 영역 정의를 바꾼다.
3. 규칙 문서 묶음마다 커밋 하나: 규칙 문서와 설명 문서를 만들고, 옛 문서를 지우고, 그 묶음을 가리키던 링크와 디스크립터를 고치고, 색인을 다시 만들고, 보존 대조를 돌린다 (ref: [move-cascade.md](../../AGENTS/epistemic-rules/folder-structure/move-cascade.md)). 커밋마다 형식 감사가 위반 0건이어야 한다.
4. 기계 규칙 파일, 도구, 시험.
5. 감사 확장(구성 검사).
6. 워크플로와 윤문 스킬 원본.
7. 진입점 문서(README, 루트 AGENTS.md, ontology/revision.md)와 구조 평가 문서를 고치고 전체 교차 확인을 한다.
8. 이 레포 문서에 도구를 돌려 결과를 확인하고, 형식 감사, 코드 검토(Codex), 사용자 검토를 거쳐 머지한다.

### 위험

- 이 레포 밖에서 옛 세부 규정 경로를 가리키는 링크가 끊긴다. 머지 전에 사용자의 다른 클론에서 찾아 사용자에게 알린다.
- 이전하며 문구가 빠지거나 다른 조항 아래로 옮겨질 수 있다. 보존 대조의 문구 차이가 0건이어야 다음 묶음으로 넘어간다.
- 윤문 대상 글이나 검토 결과가 시험 자료나 로그로 이 레포에 남으면 공개 경계를 넘는다. 시험 자료는 이 레포에서 만든 예문만 쓰고, 도구는 파일을 남기지 않는다(`--write`의 대상 파일 제외).

## 기각안

- 의미 규칙, 기계 규칙, 설명, 도구, 워크플로를 모두 `implementation/`에 두기: 도구가 읽기는 쉽지만 규약이 구현 영역으로 내려가 "명세는 `architecture/`에만 둔다"는 범주 판별과 어긋난다(`@arngard` 2026-11-23 결정).
- 다른 곳에 이미 있는 윤문 도구의 코드를 옮겨 오기: 이 레포는 공개 레포와 같게 다루므로 출처가 이 레포 밖인 코드를 들이지 않고 새로 쓴다(`@arngard` 2026-11-23 결정).
- 기계 규칙을 YAML이나 TOML, Markdown으로 쓰기: YAML은 외부 패키지가, TOML은 Python 3.11 이상이 필요하다. Markdown은 표준 라이브러리로 읽을 수 있지만 문법을 따로 정의하고 검증해야 한다. JSON은 표준 라이브러리로 읽고 형식 검증이 단순하다.
- 경계를 문장과 표로 나누기: 규정 표가 설명 문서로 빠져 규칙 문서만 읽는 검토자가 핵심 기준을 놓친다.
- 흐름 표기의 화살표와 나열의 가운뎃점을 기계로 치환하기: 흐름, 항목 표시, 참조 포인터를 기계로 구별할 수 없고, 나열과 금지 사례의 제시도 구별할 수 없다.
- 기계 규칙이 코드와 인용을 일괄로 건너뛰거나 일괄로 고치기: 규약을 담은 펜스는 고치고 원문을 옮긴 펜스는 두는 규정을 어느 쪽도 지키지 못한다. 그래서 기계 규칙은 산문에만 적용하고, 다른 영역은 후보로만 보고해 의미 검토에 맡긴다.
- 문체(평어체, 존댓말)를 보존 검사에 넣기: 윤문이 갈래와 독자에 맞춰 문체를 바꾸는 경우가 있어 기계 판정의 대상이 아니다.
- 커밋 전 훅을 따로 걸기: 상류 훅이 이미 형식 감사를 부르고, 감사 확장은 상류 자산을 고치지 않고 검사를 더하는 자리다.

## 전제와 재검토 트리거

- 전제: 다른 레포의 윤문 에이전트가 이 레포의 클론을 로컬에서 읽고 도구를 실행할 수 있다. 클론 없이 원격에서 쓰게 되면 도구의 배포 방식을 다시 검토한다.
- 전제: 사용자의 머신 가운데 가장 낮은 Python은 3.9다. 도구는 3.9에서 도는 문법만 쓴다.
