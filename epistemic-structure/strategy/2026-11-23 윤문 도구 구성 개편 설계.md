# 2026-11-23 윤문 도구 구성 개편 설계

작업 트리 노드 "정식 규약을 의미 규칙, 기계 규칙, 설명, 도구, 윤문 워크플로로 구성하고 윤문 스킬 원본을 둔다"의 설계다. 구현이 끝나 결과가 규약과 구조에 반영되면 이 문서를 종결한다.

## 상황

정식 규약은 `epistemic-structure/architecture/plain-prose-rules.md`와 그 하위 문서, `implementation/`의 세부 규정 세 묶음(어휘 선택, 참조 표기, 문장 부호)에 산문으로만 있다. 규칙 본문의 절반 이상이 `implementation/`의 예시 문서 안에 예시 표와 섞여 있다 (ref: [2026-11-18 구조 평가.md](2026-11-18%20구조%20평가.md) "측정"). 기계로 검사하거나 고치는 도구는 없다.

사용자 지시(`@arngard`)는 다음과 같다.

- 2026-11-22: 규칙을 세 부류(스크립트로 완전 처리, 스크립트로 검출하고 의미적으로 수정, 읽으며 의미적으로 수정)로 나눠 부류에 맞는 폴더 배치와 일관된 형식으로 구성한다. 윤문 스킬이 처리를 시작한다.
- 2026-11-23: 윤문 워크플로, 의미 규칙, 기계 규칙, 설명으로의 링크, 도구로 구성하고 윤문용 도구 기능을 제공한다. 규정은 지금 상태를 유지한다.
- 2026-11-23 결정: 도구 코드는 이 레포에서 새로 쓴다. 규칙 본문은 `architecture`에 둔다. 구조 평가의 윤문 경로 개선안을 함께 반영한다. 윤문 스킬 원본을 이 레포에 두고 전역 설치는 이 레포 밖의 후속 작업으로 둔다.

## 대응

- 규정의 문구는 바꾸지 않는다. 조항은 자리를 옮기거나 규칙 이름(ID)을 얻기만 한다. 이전 전후의 문장을 대조하는 보존 대조로 이를 확인한다.
- 규칙 본문은 `architecture`의 규칙 문서에 둔다. 규칙 문서 하나는 검토자 한 명이 한 번에 맡는 묶음이고, 규칙 하나가 `##` 절 하나다.
- `implementation`은 규약을 글에 적용하는 수단을 담게 다시 정의한다. 하위 프로젝트 `implementation/revision/`에 설명(예시), 기계 규칙, 도구, 워크플로, 윤문 스킬 원본을 둔다.
- 도구는 표준 라이브러리만 쓰는 Python으로 새로 쓴다. front matter가 없는 글과 표준 입력(커밋 메시지, 대화 응답)도 받는다.
- 2026-11-18 구조 평가의 윤문 경로 개선안 1, 3, 6, 7, 8을 함께 반영한다.

| `implementation/revision/tools/` | 없음 | 검출, 기계 수정, 검토 자료 수집, 보존 검사 도구와 시험 |

- 문장으로 된 조항(규칙과 그 곁의 즉각적 취지)은 모두 규칙 문서로 간다. 예시 표와 코드 예시는 설명 문서로 간다. 경계가 문장과 표 사이라 이전 결과를 기계로 대조할 수 있다.
- 기계 규칙의 규정 문장("가운뎃점(U+00B7)은 쉼표로 바꾼다")은 규칙 문서에 남는다. 기계 규칙 파일은 그 규칙 이름을 가리키며 찾을 패턴, 바꿀 표기, 건너뛸 영역만 담는다.
- 하위 프로젝트 내부는 형식 감사가 검사하지 않는다. 설명 문서와 워크플로 문서는 그래도 front matter와 이 레포의 평서문 기록 규약을 지킨다. 다른 레포의 윤문 에이전트가 읽는 문서이기 때문이다.

### 형식

#### 규칙 문서

```markdown
## <규칙 제목> `<규칙 이름>`

<조항 본문. 지금 문구 그대로>

### 후보 검출 패턴

    (정규식 코드 펜스. 검출 후 의미 수정 부류일 때만)

### 기계 규칙

- [<파일>](../../../implementation/revision/mechanical/<파일>) (완전 처리 부류일 때만)

### 설명

- [<설명 문서>](../../../implementation/revision/explanations/<문서>) "<절 제목>"
```

- 규칙 이름은 영문 소문자 케밥 케이스이고 레포 전체에서 하나다.
- 부류는 절의 구성으로 드러난다. `### 기계 규칙`이 있으면 완전 처리, `### 후보 검출 패턴`만 있으면 검출 후 의미 수정, 둘 다 없으면 의미 수정이다.
- 지금 하위 문서의 `##` 절이 하나의 조항을 여러 절로 나눠 설명하면(예: `bullets-and-prose.md`의 "개조식으로 쓰는 경우", "판정") 그 절들을 `###`로 내리고 규칙 절 하나로 묶는다.

#### 설명 문서

규칙 문서와 같은 이름의 문서에 모은다. 절 제목은 지금 세부 규정의 절 제목을 그대로 쓰고, 제목 아래 `규칙: \`<규칙 이름>\`` 줄을 둔 뒤 예시 표를 옮긴다.

#### 기계 규칙 파일

Markdown 파일 하나가 규칙 하나다. front matter 다음에 `규칙: \`<규칙 이름>\`` 줄, `## 치환` 절마다 `regex` 펜스(찾을 패턴)와 `text` 펜스(바꿀 표기), `## 건너뛸 영역` 목록을 둔다. TOML이나 YAML 대신 Markdown을 쓰는 것은 표준 라이브러리만으로 읽기 위해서다. TOML을 읽는 `tomllib`는 Python 3.11부터 있고, 사용자의 macOS 머신의 시스템 Python은 3.9다.

### 조항 이전 원장

부류: 완전 = 스크립트로 완전 처리, 검출 = 스크립트로 검출하고 의미적으로 수정, 의미 = 읽으며 의미적으로 수정.

| 지금 자리 | 규칙 문서 | 부류 |
|---|---|---|
| plain-prose-rules.md "어휘는 정확성을 우선한다", vocabulary.md, word-choice/loanwords.md, word-choice/common-usage.md | vocabulary.md | 의미. "별", "국면", 사람을 여격으로 받은 "짚다"는 검출 |
| plain-prose-rules.md "문장은 담백한 평서문으로 쓴다" | sentence.md(신설) | 의미. 날짜와 시간 표기는 검출 |
| plain-prose-rules.md "서식과 기호는 절제한다", punctuation/ascii-punctuation.md | format.md(신설) | 가운뎃점과 흐름 표기의 화살표(U+2192)는 완전. em dash, 이모지, 장식 기호, 항목 표시 화살표는 검출. 나머지는 의미 |
| plain-prose-rules.md "개조식과 줄글은...", bullets-and-prose.md | bullets-and-prose.md | 의미 |
| plain-prose-rules.md "참조는 본문 링크를 우선하고...", reference-notation/의 세 문서 | reference.md(신설) | 의미. 옛 표기 `cf.`, `ref.`와 순서나 위치로 가리킨 말은 검출 |
| plain-prose-rules.md "구성은...", "요약과 전재는...", "사실과 의견을 구분한다", composition.md | composition.md | 의미 |
| plain-prose-rules.md "문서는 기록하는 시점의...", document-temporality.md | document-temporality.md | 의미 |
| plain-prose-rules.md "기존 글을 고칠 때는...", "글의 자연스러움은..." | revision-principles.md(신설) | 의미. 모든 검토자가 함께 읽는 윤문 원칙 |

- 같은 조항이 상위 요지와 세부 규정에 두 번 적힌 경우(예: vocabulary.md의 "별" 요지와 common-usage.md의 "별" 절)는 세부 규정의 문장을 규칙 본문으로 삼는다. 요지에만 있는 문장은 같은 규칙 본문에 더한다. 문장을 지우는 경우는 다른 자리에 같은 문장이 남을 때뿐이다.
- 완전 처리 부류가 둘뿐인 것은 규정을 바꾸지 않기 때문이다. 상류 약식 규칙에만 있는 말줄임표와 둥근 따옴표의 ASCII 치환, 범위 표시의 물결표는 규정 변경이라 이 작업에 들이지 않는다(작업 트리의 다른 노드).
- 규칙 이름은 이전하면서 붙이고 결과는 규칙 문서가 담는다.

### 도구

`implementation/revision/tools/`에 둔다. 모두 파일 경로나 표준 입력을 받고, front matter가 없어도 처리한다. 출력은 사람용 텍스트와 에이전트용 JSON(`--format json`)이다.

| 도구 | 하는 일 | 종료 코드 |
|---|---|---|
| `detect.py` | 기계 규칙 위반과 후보 검출 패턴 위치를 리포트한다. 글을 고치지 않는다 | 0 위반 없음, 1 위반 있음, 2 규칙 읽기 실패 |
| `fix.py` | 기계 규칙을 적용한다. `--dry-run`은 바뀔 곳만 보인다. 표준 입력이면 표준 출력으로 낸다 | 0 성공, 2 규칙 읽기 실패 |
| `collect_review.py` | 윤문 원칙, 고른 규칙 문서의 본문, 후보 위치, 설명 경로를 검토 자료 하나로 묶는다. `--docs`로 규칙 문서를 고른다 | 0 |
| `check_preservation.py` | 고치기 전과 뒤를 대조한다. 숫자, 인라인 코드, 코드 블록, URL, 링크 대상, 인용 블록, front matter 값이 남았는지 본다 | 0 통과, 1 경고, 2 채택 금지 |

- 공통 모듈은 규칙 문서, 기계 규칙 파일, 설명 문서를 읽고, 글을 영역(front matter, 코드 펜스, 인라인 코드, 인용 블록, 링크 대상, URL, HTML)으로 나눈다. 원형 부호를 쓰는 영역(format.md의 "원형을 쓰는 영역")은 건너뛸 영역으로 들어간다.
- 보존 검사는 윤문의 정의(뜻을 유지한다)와 revision-principles.md의 "원문과 대조해 세부가 빠지지 않았는지 확인한다"를 기계로 돕는다. 문체(평어체, 존댓말)는 갈래와 독자에 따라 바뀔 수 있어 보지 않는다.
- 시험은 `tools/tests/`에 표준 라이브러리 `unittest`로 둔다 (ref: [coding-guidelines.md](../../implementation/AGENTS/epistemic-rules/coding-guidelines.md) "성공 기준을 테스트로").
- 구성 검사는 감사 확장 `AGENTS/audit-checks/revision_rules.py`로 둔다 (ref: [audit-extensions.md](../../AGENTS/epistemic-rules/audit-extensions.md)). 규칙 이름의 중복과 누락, 설명 링크의 대상과 `규칙:` 줄의 일치, 정규식 컴파일, 기계 규칙 파일이 가리키는 규칙의 존재를 본다. 형식 감사와 커밋 전 훅이 이미 감사를 부르므로 따로 훅을 걸지 않는다.

### 워크플로와 윤문 스킬

- `workflows/detect.md`: 글을 고치지 않고 리포트만 받는다.
- `workflows/revise.md`: 갈래를 정한다, 기계 수정, 의미 수정(맥락 없는 검토자가 규칙 문서 묶음별로), 기계 검사 재실행, 보존 검사, 맥락 없는 검토자의 자연스러움 확인 순서다. 갈래 규약이 아직 없는 갈래(회고, 창작, 주석)는 사실 서술 부분에 평서문 기록 규약을 적용한다 (ref: [writing-genres.md](../ontology/writing-genres.md) "경계").
- `workflows/change-rules.md`: 규칙, 패턴, 설명, 기계 규칙을 더하거나 고칠 때 고칠 파일과 구성 검사.
- `skill/SKILL.md`: 윤문 요청에서 시작해 revise.md를 따르게 하는 스킬 원본이다. 다른 레포에서 이 레포를 찾는 경로는 설치 때 정한다.

### 진입점과 구조 평가 반영

- README.md의 윤문 안내를 바꾼다. 윤문의 정의 한 문장(평가 3), 갈래와 규약 파일 표(규약이 없는 갈래는 없음으로 적는다, 평가 7), 윤문 워크플로와 규칙 문서로 가는 직접 링크(평가 1)를 둔다.
- 상위 문서(plain-prose-rules.md)는 조항을 열거하지 않는다(평가 6). 세부 규정 묶음의 안내 문서 세 건(`implementation/*/README.md`)은 묶음과 함께 사라진다(평가 8).
- 평가 2(상류 약식 규칙 조항 들이기), 4(참조 표기 두 벌), 5(늘 적재되는 약식 규칙)는 이 작업에서 다루지 않는다. 반영한 항목만 구조 평가 문서에서 지운다.
- 고칠 문서: category-placement.md, implementation.md, implementation/AGENTS.md, implementation/INDEX.yaml, README.md, README.en.md, 루트 AGENTS.md의 평서문 기록 규범, ontology/revision.md, 생성 색인.

### 진행 순서

각 단계가 커밋 하나 이상이다.

1. 설계 검토(Codex)와 사용자 승인.
2. `implementation/revision/` 골격, README, 공통 모듈과 시험의 틀.
3. 규칙 문서 묶음마다 이전: 규칙 문서와 설명 문서를 만들고 옛 문서를 지운다. 묶음마다 보존 대조를 돌린다. 보존 대조는 main의 옛 문서와 새 트리에서 문장과 표 행을 모아 빠진 것과 새로 생긴 것을 보이는 일회용 스크립트이며 `.tmp/`에 둔다.
4. 기계 규칙 파일, 도구, 시험.
5. 감사 확장(구성 검사).
6. 워크플로와 윤문 스킬 원본.
7. 영역 정의와 진입점 문서, 구조 평가 문서 갱신, 들어오는 링크의 연쇄 갱신 (ref: [move-cascade.md](../../AGENTS/epistemic-rules/folder-structure/move-cascade.md)).
8. 이 레포 문서에 도구를 돌려 결과를 확인하고, 형식 감사, 코드 검토(Codex), 사용자 검토를 거쳐 머지한다.


### 위험

- 다른 자리에서 옛 세부 규정 경로를 가리키는 링크가 끊긴다. 이 레포 안은 연쇄 갱신과 형식 감사로 잡는다. 이 레포 밖에서 가리키는 곳은 머지 전에 찾아 사용자에게 알린다.
- 이전하며 문장이 빠지거나 바뀔 수 있다. 묶음마다 보존 대조의 결과가 빈 차이여야 다음 묶음으로 넘어간다. 제목 줄과 링크 경로처럼 이전 때문에 바뀌는 줄은 대조 결과에 따로 모아 사용자 검토에 보인다.

## 기각안

- 의미 규칙, 기계 규칙, 설명, 도구, 워크플로를 모두 `implementation/`에 두기: 도구가 읽기는 쉽지만 규약이 구현 영역으로 내려가 "명세는 `architecture/`에만 둔다"는 범주 판별과 어긋난다(`@arngard` 2026-11-23 결정).
- 다른 곳에 이미 있는 윤문 도구의 코드를 옮겨 오기: 이 레포는 공개 레포와 같게 다루므로 출처가 이 레포 밖인 코드를 들이지 않고 새로 쓴다(`@arngard` 2026-11-23 결정).
- 기계 규칙을 YAML이나 TOML로 쓰기: YAML은 외부 패키지가, TOML은 Python 3.11 이상이 필요하다. 이 레포의 감사 도구와 같이 표준 라이브러리만 쓰는 쪽을 택했다.
- 문체(평어체, 존댓말)를 보존 검사에 넣기: 윤문이 갈래와 독자에 맞춰 문체를 바꾸는 경우가 있어 기계 판정의 대상이 아니다.
- 커밋 전 훅을 따로 걸기: 상류 훅이 이미 형식 감사를 부르고, 감사 확장은 상류 자산을 고치지 않고 검사를 더하는 자리다.

## 전제와 재검토 트리거

- 전제: 다른 레포의 윤문 에이전트가 이 레포의 클론을 로컬에서 읽고 도구를 실행할 수 있다. 클론 없이 원격에서 쓰게 되면 도구의 배포 방식을 다시 검토한다.
- 전제: 사용자의 머신 가운데 가장 낮은 Python은 3.9다. 모든 머신이 3.11 이상이 되면 기계 규칙 형식을 TOML로 바꾸는 안을 다시 볼 수 있다.
