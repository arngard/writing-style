# 규칙 변경 절차

규칙, 후보 검출 패턴, 설명, 기계 규칙을 더하거나 고칠 때의 절차다. 규칙 본문의 문구를 바꾸는 것은 규정 변경이므로 사용자의 결정을 받은 뒤에 한다.

## 고칠 파일

| 바꾸는 것 | 고칠 파일 |
|---|---|
| 규칙 본문 | 규칙 문서([plain-prose-rules/](../../../epistemic-structure/architecture/plain-prose-rules/))의 그 규칙 절 |
| 새 규칙 | 규칙 문서에 `` ## <규칙 제목> `<규칙 이름>` `` 절. 규칙 이름은 영문 소문자 케밥 케이스이고 레포 전체에서 하나다 |
| 후보 검출 패턴 | 규칙 절의 `### 후보 검출 패턴` 코드 블록. 한 줄에 정규식 하나를 쓴다 |
| 기계 규칙 | [mechanical/](../mechanical/)의 JSON 파일과 규칙 절의 `### 기계 규칙` 링크 |
| 설명(예시) | `explanations/`의 설명 문서 절과 규칙 절의 `### 설명` 링크 |
| 도구의 동작 | [tools/](../tools/)의 코드와 `tools/tests/`의 시험 |

- 규칙의 부류는 절 구성으로 드러난다. `### 기계 규칙`이 있으면 스크립트로 완전 처리하는 규칙, `### 후보 검출 패턴`만 있으면 스크립트로 검출하고 의미적으로 고치는 규칙, 둘 다 없으면 읽으며 의미적으로 고치는 규칙이다. 기계로 확정되는 형태만 치환하고 나머지를 후보로 보고하는 규칙은 둘 다 둔다.
- 설명 문서의 절은 제목 바로 아래 `` 규칙: `<규칙 이름>` `` 줄을 두고, 규칙 절의 `### 설명` 링크 뒤에 그 절 제목을 큰따옴표로 붙인다. 두 쪽이 서로를 가리켜야 한다.

## 후보 검출 패턴

- 오탐과 미탐 예문을 직접 만들어 `detect.py`로 확인한 뒤 넣는다. 예문은 이 레포에서 만든 것만 쓴다.
- 부호 자체를 찾는 정규식은 원형 대신 `\u00B7`처럼 이스케이프로 쓴다. 규칙과 설명에서 부호 자체를 가리킬 때 원형을 쓰지 않는다는 규정을 지키기 위해서다.
- 패턴이 넓으면 후보가 많아져 검토자의 판정 부담이 커지고, 좁으면 놓친다. 판정이 필요 없는 형태만 기계 규칙으로 옮긴다.

## 기계 규칙

- 기계가 문맥 없이 확정할 수 있는 치환만 기계 규칙으로 둔다. 확정할 수 없으면 후보 검출 패턴으로 둔다.
- JSON의 키는 `rule`, `replacements`(`find`, `replace`, `note`), `apply_in`뿐이다. `replace`의 역참조는 `\1` 형태만 쓰고, `apply_in`은 `["prose"]`다. 빈 `find`, 알 수 없는 키나 영역 이름, 컴파일되지 않는 정규식이 있으면 도구는 어떤 글도 고치기 전에 종료 코드 2로 끝난다.
- 기계 규칙을 더하면 `tools/tests/`에 낱말 경계, 코드와 인용 영역 제외, 두 번 적용해도 결과가 같은지(멱등)를 시험으로 넣는다. 시험 코드에서 부호는 `chr(0x00B7)`처럼 코드포인트로 만든다. 편집 도구가 문자열의 `\u` 이스케이프를 원형 문자로 풀어 파일에 쓰는 경우가 있어, 원형을 쓰지 않는다는 규정을 어기기 쉽다.

## 구성 검사

고친 뒤 다음을 실행한다.

1. 시험: `python -B -m unittest discover -s implementation/polishing/tools/tests -v`
2. 형식 감사: `python -B AGENTS/epistemic-rules/tools/audit.py .`. 감사 확장 [polishing_rules.py](../../../AGENTS/audit-checks/polishing_rules.py)가 규칙 이름의 중복과 누락, 설명 링크와 설명 절 `규칙:` 줄의 양방향 일치, 기계 규칙 링크와 JSON `rule` 값의 양방향 일치, 정규식 컴파일, 이 폴더 문서의 링크 대상을 본다.
3. 이 레포 문서에 `detect.py`를 돌려 새 패턴이 낸 후보를 훑어본다.
