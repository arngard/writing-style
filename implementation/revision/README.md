# 윤문 도구

평서문 기록 규약을 실제 글에 적용하는 수단을 모은 하위 프로젝트다. 규칙 본문은 [plain-prose-rules/](../../epistemic-structure/architecture/plain-prose-rules/)의 규칙 문서에 있고, 이 폴더는 그 규칙을 검출하고 고치고 검토하는 데 쓰는 자료와 도구와 절차를 담는다.

## 구성

| 폴더 | 담는 것 |
|---|---|
| [tools/](tools/) | 검출, 기계 수정, 검토 자료 수집, 보존 검사 도구와 시험 |
| [mechanical/](mechanical/) | 기계 규칙의 치환 데이터. JSON 파일 하나가 규칙 하나다 |
| [workflows/](workflows/) | 검출, 윤문, 규칙 변경 절차 |
| [skill/](skill/) | 윤문 스킬 원본 |
| `explanations/` | 규칙의 예시. 규칙 문서의 `### 설명` 절이 링크한다 |

## 기술 스택

- Python 3.9 이상의 표준 라이브러리만 쓴다. 사용자의 머신 가운데 가장 낮은 Python이 3.9이기 때문이다.
- 기계 규칙은 JSON으로 쓴다. 표준 라이브러리 `json`으로 읽고 형식 검증이 단순하기 때문이다.
- 시험은 표준 라이브러리 `unittest`로 쓰고, 시험 자료는 이 레포에서 만든 예문만 쓴다.

## 도구

모든 도구는 입력을 파일 경로나 표준 입력(`-`)으로 받고 UTF-8만 읽는다. front matter가 없는 글(커밋 메시지, 대화 응답)도 처리한다. 결과는 표준 출력, 진단은 표준 오류로 내고, `--format json`은 결과 형식만 바꾼다. 종료 코드 2는 도구 오류(규칙 읽기 실패, 입력이나 출력 실패, 잘못된 인자)다. 규칙 문서와 기계 규칙은 도구 파일이 든 이 레포의 루트를 기준으로 찾으므로, 다른 레포에서 도구를 절대 경로로 실행해도 된다.

| 도구 | 실행 | 종료 코드 |
|---|---|---|
| `detect.py` | `python <이 레포>/implementation/revision/tools/detect.py <글>` | 0 위반 없음, 1 기계 규칙 위반 있음 |
| `fix.py` | `python .../fix.py <글>`(결과를 표준 출력), `--dry-run`(바뀔 곳만), `--write`(원본을 고침) | 0 성공 |
| `collect_review.py` | `python .../collect_review.py <글> --docs vocabulary,reference` | 0 성공 |
| `check_preservation.py` | `python .../check_preservation.py <고치기 전> <고친 뒤> [--mechanical]` | 0 변경 없음, 1 확인할 변경 있음, 3 채택 금지 |

- `detect.py`는 기계 규칙 위반(산문 영역에서 `fix.py`가 고칠 곳)과 후보 검출 패턴이 일치한 곳을 영역 이름과 함께 보고한다. 후보는 의미 검토가 판정할 자리라 종료 코드에 넣지 않는다.
- `fix.py --write`는 같은 폴더의 임시 파일에 쓴 뒤 교체한다. 읽은 뒤 원본이 바뀌었으면 쓰지 않는다. 줄바꿈 형식(LF, CRLF)과 BOM(byte order mark; 바이트 순서 표시) 여부를 보존하고, 심볼릭 링크는 고치지 않고 오류로 끝낸다.
- `collect_review.py`는 윤문 원칙(`revision-principles.md`), `--docs`로 고른 규칙 문서(기본은 윤문 원칙을 뺀 전부), 후보 위치, 설명 문서 경로를 묶는다. 대상 글은 경계 표시 안에 넣어 검토 지침과 구분한다.
- `check_preservation.py`는 숫자, URL, 링크 대상, 인라인 코드, 코드 블록, 인용 블록, front matter 값의 값과 출현 횟수를 전후로 비교한다. `--mechanical`은 기계 수정 단계의 대조이며, 산문이 아닌 영역이 바뀌었으면 종료 코드 3(채택 금지)으로 끝낸다.
- 표준 입력에는 경로가 없으므로 경로로 정하는 예외는 `--path-hint <경로>`로 받는다. 대상 레포 루트 바로 아래 `reference/<자료 폴더>/` 안의 원본이면 `detect.py`와 `fix.py`는 아무것도 보고하거나 고치지 않는다. 원본은 원형 부호를 그대로 쓰는 영역이고 고치지 않는 자료이기 때문이다.
- 인자와 결과 형식의 세부는 각 도구의 docstring에 있다.

### 영역 판별

공통 모듈 [_revision_core.py](tools/_revision_core.py)는 글을 구문 영역(front matter, 코드 펜스, 들여쓴 코드, 인라인 코드, 인용 블록, 링크 대상, 참조형 링크 정의, URL, HTML, 산문)으로 나눈다. 기계 규칙은 산문에만 적용하고, 후보 검출 패턴은 모든 영역에서 찾는다. 닫히지 않은 펜스, 짝 없는 백틱처럼 판별하지 못한 구문은 그 뒤를 산문이 아닌 영역으로 보아 고치지 않는다.

### 규칙 문서에서 읽는 형식

- 규칙 절은 `` ## <규칙 제목> `<규칙 이름>` `` 형태의 제목이다. 규칙 이름은 영문 소문자 케밥 케이스다.
- `### 후보 검출 패턴` 아래 코드 블록(펜스 종류와 info string은 가리지 않는다)의 비지 않은 줄 하나가 정규식 하나다. 비ASCII 부호는 `\u00B7`처럼 이스케이프로 쓴다.
- `### 기계 규칙` 아래 링크는 `mechanical/`의 JSON을, `### 설명` 아래 링크와 그 뒤 큰따옴표 절 제목은 설명 문서의 절을 가리킨다. 절 제목은 줄 끝의 큰따옴표까지 읽으므로 제목 안에 큰따옴표가 들어가도 된다.
- 규칙 절 안의 다른 `###` 절(판정 등)은 규칙 본문의 일부로 읽고, 본문 없이 `### 설명`만 있는 규칙도 받는다.
- 설명 문서의 절은 제목 바로 아래 `` 규칙: `<규칙 이름>` `` 줄을 둔다. 한 절이 여러 규칙의 설명이면 `` 규칙: `<이름>`, `<이름>` ``처럼 쉼표로 나열한다.

## 시험

레포 루트에서 다음을 실행한다.

```
python -B -m unittest discover -s implementation/revision/tools/tests -v
```

구성 검사(규칙 이름, 설명과 기계 규칙의 양방향 일치, 정규식 컴파일, 이 폴더 문서의 링크)는 감사 확장 [revision_rules.py](../../AGENTS/audit-checks/revision_rules.py)가 맡고, 형식 감사 `python -B AGENTS/epistemic-rules/tools/audit.py .`가 실행한다.
